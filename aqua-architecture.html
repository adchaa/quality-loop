AQUA: an assured quality-adaptation loop for Firefox

Improving Firefox against ISO/IEC 25010:2023 with LLM agents, measurement gates, and a knowledge base that learns. Pilot scope: browser/extensions/newtab. — 16 October 2026

LLMs propose. Measurements decide. Humans adopt.

ISO/IEC 25010:2023 · 25023 · 25040 · 25059 MAPE-K outer loop Your agent + the aqua skill + OpenCode subagents Review agent after implementation · report agent for humans Assurance cascade Thompson-sampling planner Firefox-native promotion: try → review → Nightly → Nimbus

A quality agent should not be allowed to declare its own change “better.” In AQUA an orchestrator agent decides what to try and delegates the work to specialised subagents — but a deterministic control plane decides what counts, and a human decides what is adopted.

1. Why a different architecture

The previous prototype in loop/ is a straight pipeline: a supervisor model picks a finding, a fixer model returns one diff, a reviewer model reads it, and deterministic code checks a lint probe. That design gets several things right (evidence over model claims, isolated worktrees, human adoption), but it stands on assumptions that current research no longer supports. AQUA is built by removing those assumptions one at a time.

Models overfit whatever we measure

Agentic repair is known to overfit test suites: patches that pass the tests without fixing the defect.[19][20] A 2025 benchmark measures this directly — given “impossible” tasks, capable models delete failing tests, special-case inputs, or overload operators to pass anyway.[21] Reward hacking can also generalize into broader misbehavior.[22][23]

Models do not self-verify

LLMs asked to check their own reasoning without external feedback frequently make it worse.[17] LLM judges systematically favor their own generations (self-preference bias).[24] Juries of smaller, diverse judges are a more trustworthy alternative to one big judge.[25]

Multi-agent pipelines fail structurally

An empirical taxonomy of multi-agent LLM failures catalogs 14 failure modes in three categories: specification gaps, inter-agent misalignment, and task verification.[26] “More agents” is not a design; contracts, role separation, and independent verification are.

Speed-ups must be measured, not assumed

A randomized trial with 16 experienced open-source maintainers found AI assistance made them 19% slower while they believed it made them faster.[27] Any quality loop must be evaluated on net outcomes, with baselines and error bars, not on vibes.

At the same time, the capability is real and needs no exaggeration: Agentless resolved 32% of SWE-bench Lite for $0.70 per issue with a fixed localize–repair–validate workflow and no autonomous decision-making.[9] At Google, an agentic repair baseline produced plausible patches (passing the bug’s tests) for 73% of machine-reported bugs.[15] At Meta, assured test-improvement shipped to production with 73% of recommendations accepted by engineers.[7] The problem is not whether LLMs can write patches; it is what decides that a patch is an improvement.

Say it like this: “Two findings motivate everything that follows. First, agents happily optimize the metric instead of the goal — so our metric must be hard to game and externally checked. Second, agents can't reliably grade their own work — so the grader is never the author.”

Six design requirements

# Requirement Answer in AQUA
R1 One source of truth for quality: measured evidence, never model opinion. Quality vector q built only from probe outputs; no LLM produces a score anywhere.[2]
R2 Non-compensatory gates: a gain in one characteristic can never cancel a loss in another. Pareto acceptance on q + hard gates; no weighted sums.[6]
R3 Separation of roles: author ≠ verifier ≠ decider; diverse critics over self-review. Implementer ensemble, deterministic cascade, a reviewer agent that must be a different model, a reporter, and the human.[17][24][25]
R4 Rules are enforced at runtime, not requested in prompts. The orchestrator acts only through the skill’s aqua script, which calls a control daemon; the daemon enforces invariants I1–I5 in code, in the style of AgentSpec runtime enforcement.[32] Control plane and data plane are separated, as in CaMeL’s defence against prompt injection.[33]
R5 Everything reproducible and observable; uncertainty reported, not hidden. Event-sourced run record,[11] SARIF findings,[37] OpenTelemetry GenAI spans,[38] error bars on every reported claim.[34]
R6 The architecture itself must be falsifiable. Pre-registered RQs, equal-budget comparisons, ablations for every mechanism (section 11).[27]

Kept from the prototype because it earned its place: the tool probes and normalize.py, isolated Git worktrees, the accepted-false-positive list, the rule that a reviewer's PASS can never override a failed gate, and the human adoption boundary.

2. Quality model: ISO/IEC 25010:2023, operationalized

ISO/IEC 25010:2023 defines nine product-quality characteristics and renamed several from the 2011 edition (usability → interaction capability, portability → flexibility) and added safety.[1] ISO/IEC 25023 supplies the companion machinery: a catalogue of quality measures attached to those characteristics and subcharacteristics — and it deliberately does not assign numeric ranges or grades, because those depend on the product and its context and must be chosen locally.[2] ISO/IEC 25040 frames the evaluation itself as a managed process.[3]

That division of labour is exactly AQUA's contract. The standard gives the vocabulary; we give the numbers, in a versioned file, and calibrate them empirically.

Quality is a vector, not a score

q = ( qfunc, qperf, qinteract, qsec, qmaint, … )

Each component carries its own units and its own uncertainty. They are never added into one number.

Acceptance is Pareto

A candidate is accepted only if no characteristic gets worse and the target characteristic improves beyond a noise floor ε. Per-measure ε is calibrated from repeated runs.

Scope is declared, not implied

Characteristics outside the pilot are listed as out of scope with a reason. Unmeasured quality is a gap, never a pass.

The loop is itself a system to evaluate

ISO/IEC 25059 extends the SQuaRE quality model to AI systems;[4] section 11 applies it to AQUA: effectiveness, safety, cost, oversight.

From characteristics to Firefox measurements

ISO 25010:2023 characteristic Sub-characteristic Firefox probe → measure Target for the loop
Functional suitability functional correctness mach Jest / xpcshell / mochitest suites → pass rate; bug reproducer → fixed / not fixed Reproducer flips 0→1 with a positive control; no new failures
Performance efficiency time behaviour, resource use Talos / Browsertime benchmarks recorded in Perfherder[40]; New Tab bundle size (kB) No statistically significant regression
Interaction capability inclusiveness, operability mochitest a11y_checks[42]; axe; keyboard-operability tests Violation count does not increase; target fixes reduce it
Security confidentiality, integrity Semgrep rules; eslint-plugin-no-unsanitized[43]; targeted security tests Hard gate: no new high-severity findings; target finding resolved
Maintainability analysability, modifiability, testability ESLint; Lizard (cyclomatic complexity); jscpd (duplication); mutation score where configured Target measure improves; nothing else degrades past ε

Explicitly out of scope for the pilot, and recorded as such in the contract: compatibility, reliability, flexibility, safety (no applicable hazard analysis for New Tab), and all quality-in-use characteristics. Adding one back is a contract change, reviewed like code.

Say it like this: “ISO tells us quality has nine faces. It explicitly refuses to give us numbers, because numbers depend on the product. So we write our own numbers — per measure, with noise floors — and we never allow a big win on one face to buy silence on another. That single design decision is what separates AQUA from a scoring rubric.”

3. The architecture: two loops and a knowledge base

AQUA is a self-adaptive system in the classic MAPE-K sense: Monitor, Analyze, Plan and Execute over shared Knowledge.[5] Its modern twist has two parts.

  • Who drives the loop. An orchestrator agent, chosen and started by the human, reads a playbook and drives the loop by delegating to subagents.
  • What the effector produces. Not a deployment, but a proposal. It must survive an assurance cascade, an independent review agent and a human.

Firefox is the managed system. Probes are the sensors. Reviewed patches are the effectors. The knowledge base makes round n+1 smarter than round n.

control plane

Deterministic code: the AQUA control daemon, reached only through the skill’s aqua script. It enforces scope, budgets, gates and the two-key commit. No model can mark a failed check green.

reasoning plane

The orchestrator decides what to try next. Subagents localize, implement, review and report. They are all read-only.

evidence plane

Probes and measurements produce the facts: findings, the quality vector q, before/after logs, and the patch series.

4. Orchestration: an agent that delegates, a controller that decides

The human starts a conversation in T3 Code with the agent of their choice (Claude Code, Codex, OpenCode, ...) and invokes one skill, aqua. Its SKILL.md contains everything the orchestrator needs: its rules, the commands, the protocol and the decision heuristics. A script shipped with the skill is its only way to act. From then on the orchestrator works like a tech lead. It chooses findings, writes briefs and delegates to specialised subagents. It decides when to retry, when to ask for a second opinion, and when to give up.

This is the orchestrator–workers pattern[12] used by production multi-agent systems.[28][31] AQUA adds one rule: the orchestrator can act only through tools, and the tools carry the guarantees. This is the LLM-Modulo idea: LLMs generate and plan, external verifiers decide.[30]

Why the orchestrator is an agent, and why that is still safe

What the agent adds

Judgment that is hard to script:
  • skipping a likely false positive;
  • avoiding a model that keeps timing out;
  • sharpening a brief after an F3 rejection;
  • escalating a dubious review.
Fixed pipelines cannot adapt like this.[9][44]

What the agent cannot do

It cannot edit files, run shell commands or spawn its own helpers (all denied by the harness). It cannot commit without the two keys or exceed a budget. Every “no” comes from code, not from the prompt.

Failure modes, designed out

The multi-agent failure taxonomy[26] lists missing specifications, inter-agent misalignment and missing verification. In AQUA:
  • the playbook is the specification;
  • the controller builds every subagent prompt from evidence;
  • verification never depends on an agent’s word.

Swappable, so it is measurable

A scripted driver calls the same tools in a fixed order. “Does an agentic orchestrator beat a fixed protocol?” becomes a controlled experiment (RQ4) instead of a belief.

The five invariants (enforced in session.py, unit-tested)

# Invariant Mechanism Rationale
I1 Sole writer A fingerprint of the component in the worktree is checked before every measurement and every commit. Any foreign change stops the session. Measurements are only meaningful if nobody else touches the code.
I2 Two-key commit aqua commit requires F1–F5 to have passed on exactly this content and an approve review for exactly this candidate. If the reviewer is unavailable, the commit is refused. Assured LLM-based SE[6]: measurements and review are both necessary, neither alone is sufficient.
I3 Independent review The reviewer is a separate agent with a fresh context; the controller picks a model that differs from the implementer’s whenever one is configured, and can be told to require it. LLM judges favour their own generations[24]; diverse judges are more reliable.[25]
I4 Budgets Rounds, implementer calls per round, total agent calls, and reviewer escalations per session (3 by default). Bounded cost and bounded “ask until approved”.
I5 Grounded report The reporter writes prose. The controller appends its own evidence tables and flags any committed patch the prose omits. A human must never act on a number a model invented.
Say it like this: “The orchestrator is the tech lead: it decides what to work on and who works on it. But it has no keyboard. It can't write code, can't run commands, and can't press merge. It can only ask the control plane, and the control plane says yes only when the measurements and an independent reviewer both say yes.”

5. One round: localize → implement → measure → review → commit

A round is one finding. The orchestrator opens it, and the controller re-runs the finding’s probe to confirm it still reproduces. Then the orchestrator walks a fixed protocol with agentic steps. This follows Agentless’s lesson that a well-defined localize–repair–validate pipeline beats a free-roaming agent at a fraction of the cost.[9] The new step is review after implementation: only candidates that already passed every measurement reach the reviewer, so the reviewer spends its attention on what measurements cannot see.

Step Who What it returns Bound
Choose Orchestrator, advised by the bandit One finding and a rationale (logged; overrides are reported) Round budget; parked findings excluded
Localize Subagent with MCP probe tools[36] Region, summary, risks to preserve, strategy, false-positive flag Read-only; about 10 tool calls
Implement ×N Heterogeneous model ensemble, in parallel Search/replace edits and a causal hypothesis Typed output; ≤ 80 changed lines; k calls per round
Measure Controller: cascade F1–F5 (section 6) Per-candidate verdict, Δq, rejection reason Each filter is a hard stop
Review Subagent, fresh context (a different model when configured); escalation for a second opinion approve / request_changes / reject, with line comments Only F1–F5 survivors; fails closed
Commit Controller Patch in series/, q re-measured incrementally Two keys (I2); never touches the user’s checkout

6. Measure, then review: the assurance cascade

This is Meta’s Assured LLM-based Software Engineering principle. An LLM output is accepted only if a series of semantic filters shows that it does not regress existing properties and does improve something measurable, with the human as final reviewer, exactly as for human-authored code.[6] The filters run cheapest first. The reviewer agent comes last, so it only sees candidates the measurements could not fault.

  • F1–F2 turn a patch into a claim: a specific probe, a pinned revision, and a before/after output pair.
  • F3 is the non-compensatory core (R2). An “improve maintainability, degrade accessibility” patch dies here.
  • F5 targets known gaming strategies: suppression comments, deleted API, gutted code. It is cheap because it is mostly a diff-grammar check. The planned extension is mutation-guided hardening tests in the style of Meta’s ACH.[8]
  • The review gate adds judgment with limited authority. The reviewer can block anything and comment on everything. It can approve only what the measurements already accepted. Its request_changes comments become the next implementer’s brief.

Promotion stays human, and follows Mozilla’s own ladder

A committed candidate is not merged. It becomes a reviewable patch that follows the standard Firefox path:

  1. a mach try CI push for the touched suites[39];
  2. a Phabricator review;
  3. for anything user-visible, a Nightly rollout watched with Perfherder[40], plus a Nimbus experiment if there is a product-level claim.[41]
Say it like this: “The patch first has to prove it exists (F1), that it did something (F2), that it did nothing bad anywhere else (F3), that nothing broke (F4), and that it didn't cheat (F5). Only then does a reviewer from a different model family read it, and only then does a human see it.”

7. Plan: a bandit that advises the orchestrator

Which ISO characteristic deserves the next round? AQUA treats each characteristic as an arm of a multi-armed bandit. Each arm keeps a Beta(α, β) posterior over “a round on this characteristic ends with a committed, measured improvement”. Thompson sampling draws θ from each posterior and divides by the arm’s relative cost (mean seconds per round). The highest score wins, and the best finding of that arm is suggested by priority.[10]

Exploration for free

Uncertain arms sometimes win the draw, so a characteristic that failed early is retried later instead of being abandoned. Successful, cheap arms win most draws.

Rewards

A committed patch adds α + 1; a failed round adds β + 1. A human reject later adds β + 1 again, so the planner learns what humans adopt, not only what the cascade passes.

Advisory, by design

The orchestrator may override the suggestion (for example a likely false positive in build scripts). It must state a rationale, and the report shows every divergence.

8. Knowledge: what makes round n+1 better

ledger

q after every round of every session: the evidence trail behind every quality claim.

bandit

The posteriors and cost per characteristic, persisted across sessions.

playbook

Committed fixes per rule, retrieved as examples for the next implementer on the same rule.

attempts

The failure history per finding. After 2 failed rounds a finding is parked as unresolved.

false positives

Claims by the localizer or reviewer go to a suggestion queue. Only a human moves them into the confirmed list.

candidates

Committed patches awaiting the human verdict. The verdict feeds the bandit.

9. The report agent and the human decision

When the orchestrator ends the session, the controller freezes the evidence: every round, candidate, filter result, review, diff, Δq, budget and model call. The orchestrator then delegates the reporter. Like the cited-sources agent that closes production research systems,[28] it turns raw evidence into something a busy engineer can act on:

  • a summary;
  • one section per patch: what changed, why behaviour should be preserved, what the reviewer said, the measured Δq, and what to double-check;
  • what did not work and why;
  • the q table per ISO characteristic;
  • process notes and limitations.

Grounded by construction (I5)

After the prose, the controller appends its own tables: q, rounds, candidates, commits, agent usage and posteriors. If the prose skips a committed patch, a controller note says so at the top.

The human closes the loop

aqua_loop.py feedback <id> accept|reject records the verdict. A rejection feeds the bandit, and confirmed false positives feed ANALYZE.

Everything is replayable

events.jsonl, every subagent prompt and reply, the probe logs, and the patch series apply on the recorded baseline revision.[11]

10. Agents, models and cost

Role Default Why
Orchestrator Whatever agent the human starts in T3 Code, running the aqua skill Chosen per conversation by the human. It makes decisions, not code; the controller enforces the rules whatever the agent is.
Localizer OpenCode + the aqua-probes MCP server Needs tools, not a big model
Implementers OpenCode; DeepSeek by default, more models rotate when configured Diversity raises the chance that one candidate survives; with one model it comes from sampling only
Reviewer OpenCode, a fresh context; the escalation model only when the orchestrator asks Independence (I3); second opinions are reserved for disputed or security-relevant reviews
Reporter OpenCode Writing from structured evidence

Every role defaults to opencode/deepseek-v4.1-flash-free; each can be set to any model from opencode models in aqua.yml. Escalations are rationed by agents.escalation_budget (3 per session by default); the controller counts and refuses beyond it. Every call’s model, duration and outcome appears in the report.

11. Evaluation plan

RQ Question Measure
RQ1 Does AQUA improve measured quality? Δq per characteristic per session; committed patches per round
RQ2 Are committed patches good? Human acceptance rate; reviewer/human agreement; patches rejected after commit
RQ3 Which mechanisms matter? Ablations: planner (Thompson vs random vs round-robin), N = 1 vs 3, no reflection, review vs no review
RQ4 Is an agentic orchestrator better than a fixed protocol? Orchestrator vs scripted driver, same tools and budgets: commits, human acceptance, agent calls, time
RQ5 What does it cost? Agent calls, escalations, wall time per committed patch

Report every rate with a confidence interval over repeated sessions,[34] and compare at equal budget. The METR result is the reminder that perceived help and measured help can disagree.[27]

Threats to validity

  • Construct. q covers lint, Semgrep and Lizard measures. Performance efficiency is not measured in the pilot, and F4 is off until the newtab test dependencies are installed.
  • Internal. Free models change and time out. Logging the model per call and repeating sessions mitigates this.
  • External. One Firefox component. The architecture is component-agnostic, but the evidence is not yet.
  • Reviewer validity. An LLM reviewer can miss behaviour changes. Hence the human gate, and RQ2 measures reviewer/human agreement.

12. The architecture in one paragraph

AQUA is a MAPE-K loop for ISO/IEC 25010 quality in Firefox. An orchestrator agent, chosen by the human and guided by one skill (SKILL.md and its script), plans each round with the help of a Thompson-sampling bandit. It delegates to subagents: a localizer, an ensemble of implementers, a reviewer after implementation, and a reporter at the end. Every action passes through a deterministic control daemon. That plane measures candidates with an assurance cascade (Pareto non-regression on the quality vector), commits only with two keys (measurements and an independent review), rations second opinions, and grounds the final report in its own evidence. Agents propose, measurements decide, humans adopt.

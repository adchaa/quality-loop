AQUA — Assured QUality Adaptation
~1 min

What to say

  • Everyone now has AI that writes code. Writing code fast is solved. The open question is: is the code getting better or worse?
  • To answer that, we need two things: a definition of "quality" (that's ISO/IEC 25010) and a way to measure it.
  • I built a system called AQUA that lets AI agents improve real Firefox code, but only keeps changes that measurably improve quality and that a human approves.
  • Read the motto out loud — it's the whole talk in one line.
The problem

"Better code" means nothing until you define it

What AI is good atProducing plausible changes fast: refactors, fixes, cleanups, in seconds.
What AI is bad atKnowing whether its change actually made things better. It will confidently say "improved readability" either way.
The trap"Looks good to me" from the same AI that wrote the patch is not evidence.
What we needA standard definition of quality + objective measurements + a human who decides.

AI coding benchmarks usually count a fix as "solved" when the existing tests pass. That makes it plausible — not necessarily correct, and not necessarily better.

~1.5 min

What to say

  • AI changes look convincing. That's exactly the danger: it can make code worse while describing it as an improvement.
  • So we need an external, standard yardstick. In software engineering that yardstick exists: ISO/IEC 25010.
  • Transition: "Let's look at what that standard actually says quality is."
ISO/IEC 25010:2023 — product quality model

Quality = nine characteristics

Functional suitabilityDoes it do the right thing, correctly?
Performance efficiencySpeed, resource use, capacity
CompatibilityCo-exists and interoperates with others
Interaction capabilityUsability, accessibility (was "usability")
ReliabilityKeeps working, recovers from faults
SecurityConfidentiality, integrity, resistance
MaintainabilityModularity, reusability, analysability, modifiability, testability
FlexibilityAdaptability, scalability (was "portability")
SafetyAvoids harm to people and environment

Each characteristic has sub-characteristics. "Quality in use" moved to a separate standard (ISO/IEC 25019) in 2023.

~2 min

What to say

  • ISO/IEC 25010 is part of the SQuaRE family of standards. It breaks "quality" into nine characteristics, each with sub-characteristics.
  • The 2023 revision renamed usability to interaction capability, portability to flexibility, and added safety.
  • Point at maintainability: today's demo focuses on it. Its sub-characteristics are modularity, reusability, analysability, modifiability, testability. Our example targets analysability — how easy code is to understand.
  • Key point: the standard tells you what quality is, not how to measure it. That's the next step.

~2 min

What to say

  • Each tool is a sensor. Each sensor's findings are filed under one ISO characteristic. That mapping is the bridge between the standard and the code.
  • Explain cyclomatic complexity simply: the number of different paths through a function — every if, case, && adds one. Above 15 a function gets hard to understand and test.
  • ccn_excess adds up how far every function is over 15. A function at 27 contributes 12.
  • Be honest: these are proxies. ISO/IEC 25023 defines official measures; ours are practical approximations. And we don't measure every characteristic — performance and reliability are missing.

The architecture

A self-adaptive loop: MAPE-K

MAPE-K is the classic architecture for self-adaptive systems (IBM's autonomic computing).

~1.5 min

What to say

  • The system is a loop: Monitor the code with the tools, Analyze findings into ISO categories, Plan which one to fix, Execute the fix — then measure again.
  • The Knowledge in the middle is memory across sessions: what worked, what didn't, what the human rejected.
  • This is not my invention — MAPE-K is a well-known pattern from self-adaptive systems research. The new part is putting AI agents in the Execute step, and fencing them in.
Who does what

An AI team with a referee

Orchestrator (AI)The "tech lead": picks the problem, briefs the team, decides retry / give up. Writes no code.
Localizer (AI)Explains where and why the problem is, and what must not break.
Implementers (AI)Each proposes a candidate fix, in parallel.
Reviewer (AI)Reviews fixes that already passed the measurements. Approve / request changes / reject.
Reporter (AI)Writes the final report for the human.
Controller (plain code, no AI)The referee: measures, enforces rules, only it may touch files.

Started from T3 Code with an agent of my choice + one skill file (SKILL.md). Subagents run on OpenCode (DeepSeek).

~2 min

What to say

  • Instead of one AI doing everything, it's a team with specialised roles — like a real dev team.
  • The crucial piece is the green box: the controller is ordinary code, not AI. The AIs can only ask it to do things; it measures and it says yes or no.
  • How I start it: I open a conversation, and say "use the aqua skill to run a session with 2 rounds, focus maintainability". The skill file is the instruction manual for the orchestrator.

The assurance cascade

Five gates + a review = two keys

GateThe fix is rejected when…ISO link
F1it doesn't apply cleanly, is too big (> 80 lines), or breaks parsingfunctional suitability
F2the original problem is still therethe target characteristic
F3any quality number gets worse (no trade-offs allowed)all characteristics
F4the tests fail (off in this pilot)functional suitability
F5it cheats: "ignore warning" comments, deleted code, removed exports—
Reviewthe AI reviewer does not approve—

Commit needs both keys: all measurements passed and reviewer approved. Enforced in code, not in a prompt.

~2 min

What to say

  • This is the heart of it. A fix must survive every gate. Cheap checks first, expensive last.
  • F3 is the ISO angle: improving maintainability is not allowed to make security or accessibility worse — the whole quality vector must not regress (a "Pareto" rule).
  • F5 exists because of Goodhart's law: "when a measure becomes a target, it stops being a good measure." An AI told to reduce warnings might just add // eslint-disable. F5 catches that.
  • Two keys, like a bank vault: measurements alone or review alone is not enough.
The assurance cascade · in detail

How each gate decides: measure before, patch, measure after

GateExact check in the code
F1each edit's search text matches exactly once; file changes; ≤ 80 changed lines; node --check passes; no new ESLint parse error
F2complexity: function still exists and CCN ≤ 15 · lint/Semgrep: that rule's count in the file goes down
F3for every measure: after ≤ before + ε (ε = 0); and the target characteristic's measures improve in total
F4test command exits 0; one retry for flaky tests
F5no added eslint-disable / nosemgrep / @ts-ignore…; no export removed; not > 30% of the code deleted

~2 min

What to say

  • Every gate is a few lines of plain Python, with no AI involved. The tools measure the file before the patch, the patch is applied to a temporary copy, and the tools measure it again. The gates only compare those two snapshots.
  • F1 "exactly once" matters: if the AI's search text matched twice, we wouldn't know which place it meant, so the patch is rejected instead of guessed.
  • F2 for complexity also checks the function still exists. Otherwise the cheapest "fix" would be to rename it, and the finding would disappear.
  • F3 is strict: ε is 0, so even one new warning anywhere in the file blocks the patch. That is fine for lint counts, because they are deterministic.
  • When a gate fails, the reason is sent back to the next implementer.
Planning

Which ISO characteristic to work on next?

A Thompson-sampling bandit keeps a win/loss record per characteristic.

  • Each round it draws a "lucky guess" of the success rate for each one, adjusted by cost.
  • Characteristics that keep succeeding get picked more — but the others still get a chance.
  • Human accept / reject feeds the record.

The orchestrator may override it — but must write down why.

~1.5 min

What to say

  • Analogy: a row of slot machines. You want to play the one that pays most, but you don't know which — so you mostly play the best so far and sometimes try others. That's the explore/exploit trade-off.
  • Here each "machine" is an ISO characteristic. After today's demo, maintainability looks most promising (0.80).
  • In the demo the planner actually suggested a security finding both times, and the orchestrator overrode it because I asked for focus = maintainability. It recorded that reason — the human stays in charge.

~1.5 min

What to say

  • Each curve is what the system believes about one characteristic's success rate. Maintainability has 4 wins and 1 loss, so its curve sits on the right.
  • Each round it draws one random guess from every curve, the dot. The highest guess (divided by how long that kind of round takes) is picked.
  • Because it is a random draw, security and accessibility still win sometimes. That is how it keeps exploring instead of giving up on them.
  • After the round: a kept patch is a win, a failure or a human reject is a loss. The curve moves, and the next draw is better informed.
  • The θ values shown are one example draw; the win/loss records are the real ones after the demo.

The human closes the loop

Nothing is applied automatically

  • The reporter writes report.md: each patch, why it should be safe, what to double-check by hand.
  • The controller appends its own evidence tables, so the AI can't invent numbers.
  • Patches are files in series/ — not applied to Firefox, not submitted.
  • I decide, and my verdict trains the planner:
python3 loop/aqua_loop.py feedback <patch-id> accept
python3 loop/aqua_loop.py feedback <patch-id> reject
From the real report ("double-check by hand")
  • Confirm every unmatched action still returns the same state reference.
  • No tests ran on this patch — run the Reducers test suite before accepting.
  • The two maintainability measures disagree about whether this session helped (complexity ↓, lint warnings unchanged).
~1.5 min

What to say

  • The final authority is the human. The AI's job ends with a clear report and a checklist.
  • Read one of the checklist lines from the real report — it shows the reporter is honest about uncertainty, not just cheerleading.
Honest limitations

What this does not prove

Tests were offF4 disabled (New Tab test dependencies not installed). Correctness rests on parsing, static guards and the AI review.
One model for everythingThe reviewer is the same model as the implementer, in a fresh context. Independent by context, not by model.
Partial ISO coverageNo performance, reliability or safety measures. Our measures are proxies, not ISO/IEC 25023 measures.
Metrics can disagreeComplexity improved, lint warnings didn't move. "Quality" is a vector, not one number.

Small sample: one session, two patches. Needs repeated runs and human acceptance rates.

~1.5 min

What to say

  • Say these before someone in the audience does — it builds trust.
  • The biggest one: without tests, we can't be sure behaviour is unchanged. Next step is enabling F4.
  • The design already supports different models for the reviewer; I just used one free model for this demo.
Honest limitations · measuring and planning

Where the measurements and the bandit are still weak

q only sees the edited fileA patch that breaks a file importing it passes F3. Fix: re-measure the dependent files too.
ε is 0, not calibratedFine for deterministic lint counts; noisy measures like performance will need ε calibrated from repeated runs.
The bandit never forgetsAs the easy findings in an arm get fixed, the arm gets harder, but old wins still count. Fix: discount old rewards.
Arms may be too coarseHow hard a round is depends more on the rule than on the ISO characteristic. And with 3 arms and a few rounds, it may not beat round-robin.

All four are measurable: the round-robin switch and repeated sessions tell us which ones matter.

~1.5 min

What to say

  • These are design limits, not bugs: the gates are deliberately simple so anyone can check them.
  • The single-file view is the most important. Today it is partly covered by F4 (tests), but F4 was off in the demo.
  • For the bandit: with only two rounds in the demo it hasn't learned anything significant yet. The claim that it helps has to be tested against round-robin over many sessions.
Takeaways

Three things to remember

1 · Define quality firstISO/IEC 25010 turns "better code" into nine named characteristics you can map tools to.
2 · Measure, don't trustAI output is a proposal. Deterministic gates and a non-regression rule decide.
3 · Keep the human in chargeTwo keys to commit, nothing applied automatically, human verdicts steer the next session.

Backup · likely questions

Q&A cheat sheet

Isn't the AI grading its own homework?No: the numbers come from deterministic tools (ESLint, Semgrep, Lizard), and commit needs measurements and review. Same-model review is a known limitation.
Can it game the metrics?That's Goodhart's law. F5 blocks suppression comments and deleted code; F3 forbids any regression; the reviewer checks behaviour.
Why not let the AI commit directly?Plausible ≠ correct. Without tests, a human must check behaviour.
Did it touch real Firefox?Only a temporary copy (git worktree). Patches are files; nothing submitted.
Is it expensive?Demo used a free model: 9 calls, ~19 min of agent time for 2 patches.
Why cyclomatic complexity?Widely used, tool-supported proxy for analysability and testability; easy to verify.

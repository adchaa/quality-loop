An evidence-gated agent loop for software quality

The idea in one minute

An agent should not be allowed to declare its own code “higher quality.” It proposes an experiment. Reproducible measurements and tests decide whether the experiment worked.

ISO gives the quality vocabulary. Probes produce evidence. The agent proposes a patch. A deterministic gate checks it. A human decides what to adopt.

Why this architecture?

A single “fix all findings” agent can optimize what is easy to count while missing regressions elsewhere. A large swarm of scoring agents adds coordination but does not make scores true. This design keeps reasoning flexible and decisions inspectable: every candidate patch is attached to a claim and a before/after test result.

What counts as an agent?

The executable pilot uses three model roles behind CLI boundaries: Muse Spark selects one known finding, Step 5 returns a scoped diff, and GPT-6 Luna reviews that diff and its evidence. Deterministic code controls scope, verification and acceptance. The model never writes into the user’s Firefox checkout.

Presenter talk track

“We turn ISO 25010 into a quality contract for a Firefox component. Tools measure the current behavior and create evidence-backed work items. One agent proposes one isolated patch at a time. We rerun the reproducer and risk-appropriate Firefox checks, compare the result with the baseline, and keep the patch only if the measured gain appears without crossing a hard quality gate. The run log lets us audit and reproduce the decision. The agent prepares candidates; people remain responsible for adoption.”

A natural presentation path is: problem → ISO quality model → architecture → example patch → how to evaluate the research claim.

System view

Architecture and control flow

The design has two halves: an evidence plane that measures the product, and a control plane that decides which experiment to run and whether its result passes policy. The language model works inside that boundary.

Muse Spark 1.3 · selector

Receives only the eligible finding list and returns one allowed finding ID or a stop decision. The controller rejects invented IDs.

OpenCode CLI · plan agent · JSON response

Step 5 · patch proposer

Receives one finding, source context and local instructions. It returns a one-file diff and causal hypothesis. Code applies the diff in a detached candidate worktree.

OpenCode CLI · plan agent · no direct checkout edits

GPT-6 Luna · critic

Reads the patch and deterministic evidence in a separate Codex CLI process. Its PASS is advisory; failed or missing checks still reject the candidate.

Codex CLI · read-only sandbox · schema-constrained verdict

Reasoning plane

Use AI where judgment helps

Interpret a finding, locate relevant code, propose a minimal patch, explain its expected effect, and react to test failures.

Evidence plane

Use tools for observable facts

Tests, lint, static analysis, bundle reports and browser checks return results. A model’s confidence is not a test result.

Control plane

Use code for policy

Enforce scope, budgets, test selection, non-waivable gates, rollback and stop conditions. No model can mark a failed check green.

Quality model

ISO/IEC 25010:2023: a checklist for the product

The current product-quality model has nine characteristics. It gives a shared vocabulary for specifying and evaluating product quality; it does not prescribe Firefox tools, thresholds, agent roles, or a single weighted score [1]. The pilot should map its actual measures to the relevant characteristics and explicitly label gaps.

Important design choice: keep a vector of observed measures. Use hard gates for correctness, security and regressions. A gain in one characteristic must not mathematically cancel a failure in another. Weights and numeric thresholds are local policy choices and need empirical calibration.

One experiment at a time

How the loop works

  1. Freeze the contract and baseline. Choose the component, ISO characteristics in scope, required evidence, thresholds and maximum effort. Record the Firefox revision, build and tool versions. Run baseline probes before editing.
  2. Create an evidence-backed work item. A probe result becomes a structured issue with source tool, file and location, rule, observed severity, raw artifact reference, ISO mapping and confidence caveat. Retain the original output so normalization can be checked.
  3. Select one issue by policy. Muse Spark chooses one item from the eligible finding list; controller code checks that its ID is allowed, in scope and within the round budget. The model cannot invent issues or quality scores. Low-confidence or disputed findings can be sent to a human for triage.
  4. Propose one minimal change. Step 5 receives one finding, source context and applicable Firefox instructions. It returns a single-file diff and a causal hypothesis; code applies the diff only in an isolated candidate worktree. The current prototype does not ask the model to invent tests.
  5. Try to falsify the claim. The current executable loop reruns the selected ESLint, Semgrep or Lizard probe and touched-file lint before and after the diff. Broader risk-based verification can add New Tab Jest, xpcshell, browser tests and builds; those rings are not yet called by this controller.
  6. Apply non-compensatory gates. Reject on a new required-test failure, a scope violation, a failed security / correctness gate, or a measured regression beyond policy. A patch passes only when the claimed improvement is supported by comparable before/after evidence. An unavailable or inconclusive check is “unresolved,” not “pass.”
  7. Present a reviewable candidate. Preserve the patch, logs, evidence, model / prompt version and decision. A human decides whether to apply, revise or discard the candidate. Adoption triggers a new baseline; rejection keeps the evidence and ends that attempt.

Promotion ladder

Always: reproducer when one can be written, touched-file lint, diff and scope review.

Component risk: New Tab Jest suite and relevant xpcshell tests. Compare new failures against the baseline.

High impact: browser tests, build, bundle / prerender outputs, and metrics / channel compatibility checks when touched.

These are escalating verification sets, not a promise that every tier ran. The current ring_runner.py describes commands for the tiers; the live R1 record did not execute the dynamic tiers.

Stop conditions: no eligible issue remains; all scoped gates pass; the candidate fails a hard gate; evidence is inconclusive; an iteration / time / model budget is exhausted; or repeated experiments stop producing measured improvement. Repeating an identical patch is not progress.

What one Firefox example looks like

The October 14 artifact set contains a narrow static-analysis example in browser/extensions/newtab/lib/SectionsManager.sys.mjs. It is useful for showing the evidence path, while also showing what remains unverified.

1 · ObservationSemgrep raised two Object.assign warnings in the file. Inspection distinguished a fresh-object assignment from the reported sink.
2 · CandidateA one-line property assignment replaced the flagged call at the affected location. The separate fresh-object case was left unchanged.
3 · Static evidenceThe file re-scan changed from two findings to zero. The touched-file lint artifact reports zero problems. The Codex reviewer returned PASS with the supplied evidence.
Limit of this result: this supports a narrow static-finding claim for the file. New Tab Jest, xpcshell, browser tests and a build were not run in the recorded R1 flow. It is not evidence that the complete agent loop is already implemented or that every ISO characteristic improved.
Prototype boundary: the model CLIs are now wired. The executable loop verifies supported ESLint, Semgrep and Lizard findings plus touched-file lint in an isolated worktree. It does not yet run the full New Tab Jest, xpcshell, browser-test or build rings. It records no ISO score from model output.

Run artifacts produced today

  • baseline.json + baseline-overlay.patch: base revision and tracked local-change hash.
  • events.jsonl: ordered model, probe, review and decision events.
  • models/: per-round prompt, CLI output and stderr logs.
  • evidence/: before / after probe and lint logs.
  • patches/ + decision.json: proposed diffs, measurements, reviewer notes and outcome.

Implementation boundary

Run preflight first, then pass --execute to call the models and probes. The loop copies tracked local changes into a detached Git worktree, applies the model diff there, and records every prompt, response, check and decision under loop/artifacts/runs/. It refuses to start when untracked Firefox files could be omitted. Automatic adoption, merge, push and submission stay outside the loop.

The running workflow is one controller, three distinct model roles, static verification, a read-only independent critic and a human adoption decision. Only the targeted static probe and lint run today; full Firefox test rings remain future work.

Research contribution

Make a falsifiable claim, then test it

Research question: On Firefox New Tab maintenance tasks, does an evidence-gated patch loop increase the share of changes that are independently verified without increasing regressions, compared with a one-shot coding agent under the same model and tool budget?

Primary outcomesIssue reproducer fixed; relevant tests pass; regression rate; scope-policy violations; accepted-patch correctness under human review.
Quality outcomesPer-characteristic measure changes only where valid probes exist. Report unmeasured quality as a gap, not a zero or a pass.
System outcomesWall time, tool / model cost, retries, tests run, evidence completeness and reproducibility.
Experimental designUse held-out historical issues or patches; pin revision and environment; compare equal budgets; repeat stochastic runs; report uncertainty and failures.

Ablations that answer “why?”

Compare the full loop with: (1) one-shot patching, (2) no issue-specific reproducer, (3) no independent verifier, and (4) no event / evidence record. This tests which mechanism adds value, rather than assuming that adding more agents improves the result.

Threats to validity: static-analysis counts are proxies; Mozilla test suites can be flaky; generated tests can encode the wrong expectation; quality trade-offs depend on New Tab users and product context; thresholds and issue selection can bias results. Keep raw artifacts, use held-out tasks, and have people validate the high-impact conclusions.
Research grounding

Sources and what they support

These sources motivate the mechanisms. They do not prove this Firefox system works; that is the empirical question above.

  1. ISO/IEC 25010:2023 — Product quality modelPrimary standard page. Defines a nine-characteristic product-quality model and presents it as a reference for specifying, measuring and evaluating product quality. ISO defines the quality model, not the local Firefox thresholds or agent workflow.
  2. Wang et al. “The OpenHands Software Agent SDK: A Composable and Extensible Foundation for Production Agents.” MLSys 2026.Primary research. Supports typed tool boundaries, a single event-sourced conversation state, replay / recovery and modular agent execution. Its reported deployment results belong to OpenHands, not this proposal.
  3. Yang et al. “SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering.” NeurIPS 2024.Primary research. Supports designing repository navigation, editing and test execution as a useful agent-computer interface; it does not imply an agent should control release policy.
  4. Mündler et al. “SWT-Bench: Testing and Validating Real-World Bug-Fixes with Code Agents.” NeurIPS 2024.Primary research. Finds issue-reproducing generated tests can filter candidate fixes; the paper reports a precision improvement on its benchmark. This motivates reproducer-first validation, not trusting agent-authored tests without checking them.
  5. Zhang et al. “SWE-bench Goes Live!” NeurIPS 2025.Primary benchmark research. Motivates realistic, current repository tasks and reproducible execution environments when evaluating software agents.
  6. OpenCode CLI documentationDocuments non-interactive model invocation and JSON output used by the Muse Spark selector and Step 5 diff proposer.
  7. OpenAI Codex CLI documentationDocuments schema-constrained output and sandbox options used for the GPT-6 Luna read-only review.

Closing summary

Keep the architecture memorable: define quality → measure → choose → patch → falsify → review. The contribution is not a clever swarm. It is a traceable method for turning a quality claim into an isolated change whose value must survive independent evidence.
